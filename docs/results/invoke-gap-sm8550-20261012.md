## Buffer contract

Method 2 (`0x02040100`) passes four inputs and one output. Every payload is
a managed byte array held by a pinned GCHandle for the batch. Pinning keeps
its CPU address stable; it does not create a registered DMA allocation.

| Argument | Bytes | Allocation |
| --- | ---: | --- |
| Config | 4 | Pinned managed array |
| Activations | 202,624 | Pinned managed array |
| Weights | 69,683,200 | Pinned managed array |
| Tables | 2,601,344 | Pinned managed array |
| Output, including workspace and telemetry | 22,519,808 | New pinned managed array per invocation |

The host remote_arg array is an 80-byte AllocHGlobal allocation (five
16-byte ARM64 entries). The unsigned-PD control structure is an 8-byte
AllocHGlobal allocation. The open URI is a pinned managed UTF-8 array;
neither is a synthesis buffer argument.

The Samsung SM8550 FastRPC header declares `copybuf` with the comment
**"used to copy non-ion buffers"**:
`samsung-dm1q-s911b-kernel` revision
`854fa44673fa7c216815676e3f4f3be4264ab0a0`,
`Kernel/kernel_platform/msm-kernel/drivers/char/adsprpc_shared.h:870`.
This is source evidence of the copy mechanism, not proof of the installed
vendor binary's complete implementation. The controlled phone probe below
establishes the size-dependent cost on the actual path.

The FastRPC API header also describes registration as **"enable zero-copy
sharing with DSP via SMMU"** (`fastrpc` revision
`d247519650fe5cb16de6c78edaa95bcc4be25073`, `inc/remote.h:1225`).
Its `fastrpc_mmap` contract at lines 1168–1197 states that mappings persist
until unmapping or session close and that pointer arguments incur driver
cache maintenance. Shared allocation is therefore distinct from pinning,
and persistent pointer arguments do not imply zero per-call cache work.

## Timing and causal probe

Stopwatch timestamps bracket argument allocation/preparation, the existing
managed delegate invoke, and output processing. They are managed call-site
timestamps, not hooks inside the vendor library. Output processing includes
telemetry, PCM extraction and hashing; run 0 also writes the output file and
builds the playback array. Instrumentation and receipt formatting occur
outside the invoke timer. The raw timestamp frequency is recorded per run.

First instrumented batch: warm medians (runs 1–5) were 141.246 ms invoke,
99.063 ms DSP, 1.886 ms setup and 0.502 ms output handling. First invoke was
165.358 ms. The original receipt's setup/output exclusion is confirmed;
those phases cannot explain its 39.146 ms invoke-minus-DSP gap.

A second batch retained the same six successful synthesis calls, then used
the worker's existing unsupported-method return: method 127, with the same
four-input/one-output scalar counts (`0x7F040100`). The inherited dispatch
in `src/jobs/Kokoro.HmxConvRun.ps1` returns 20 before reading payloads or
acquiring compute resources. All 18 diagnostic calls returned 20. They
produce no PCM and do not replace the saved synthesis output. Cases run in
Full, Small, WithoutWeights order, six repetitions on the same handle;
repetition 0 is excluded from medians.

| Case | Changed declared lengths | Warm median invoke ms |
| --- | --- | ---: |
| Full | Original five lengths | 24.251 |
| Small | All five lengths = 4 | 0.352 |
| WithoutWeights | Only weights length = 4 | 6.585 |

The full-minus-small difference is 23.899 ms, 61.1% of the original
39.146 ms gap. Full-minus-WithoutWeights is 17.666 ms. These are differences
of medians, not separately measured kernel memcpy durations. They establish
that buffer-size-dependent handling explains most of the original gap and
that weights are its largest measured contributor. The unsupported-return
probe does not reproduce resource acquisition, successful-return behavior,
or all DSP cache effects; the remaining gap is **unattributed**.

The second synthesis batch had warm medians 142.662 ms invoke and 99.230 ms
DSP. All twelve synthesis calls across both batches matched baseline PCM
SHA256 `67E722EF3D6D3671ADFC8E15ADC870A9A0A5EC91C15B0A4E0F398D6B4BB66028`.
Both batches played 51,000 frames and reported zero xruns and verified
startup restoration. No new listening assessment was made.
